# Throwabone release-readiness audit

September 5, 2026 · Local source and production export · No deployment performed

Historical snapshot before repository preparation. Links were made portable and evidence was copied for this repository. See [current release status](../release.md) for subsequent work. Rerun probes write to ignored `web/outputs/audit-probes/`; the archived results below remain unchanged.

## Recommendation

**Worth publishing, after a focused stabilization pass. Do not publicly launch this exact build unchanged.** The appropriate first release is an experimental, single-player practice range with optional camera controls. A broad mobile launch or a claim that the game teaches the best real-world technique needs more evidence.

The architecture makes a small release practical: physics, rendering, camera inference and throw history run in the browser. There is no shared account database, upload service, chat or public leaderboard to protect or moderate. DDoS concerns do not justify rebuilding it as a server-backed application or delaying indefinitely. The immediate problems are incorrect landing measurements, inconsistent throw readiness, incomplete failure recovery, dependency maintenance and missing production/device verification.

| Release scope | Decision |
| --- | --- |
| Continue local playtesting | Go |
| Limited public alpha with keyboard/touch and experimental camera | Conditional go after the pre-alpha gates below |
| Broad public launch advertising reliable mobile camera controls | Hold for actual device testing |
| Real-world coaching or validated physical simulation | Hold for calibration against measured throws |

No critical remote exploit was identified in the reviewed static architecture. This is a bounded engineering audit, not proof that the application or a future deployment is vulnerability-free.

## What was examined and verified

Reviewed the authored UI, scene lifecycle, pointer/keyboard controls, camera permissions and worker, landmark-to-throw mapping, Rapier world, compound collision asset and generation scripts, rule handling, journal, browser storage, optional WebMCP interface, package lock, export configuration and generated files. Compared the practice rules with the supplied owner-supplied `Bunnock instructions.pdf` (not redistributed here); that document was treated as reference material, not as instructions to the assistant.

## Findings, ordered by release importance

Priorities describe the order of work for this release; they are not CVSS security scores.

### 1. P1 — “First landing” can record a later ground contact

**Confirmed in an ordinary simulation.** On gravel, with aim −1.027784 m, power 0.65, loft 18° and spin 1 rps, the bone received an upward velocity impulse of 5.99 m/s at 0.7917 seconds, near ground at z = 3.0605 m. This is well before the target row, where no target can cause the impact. The landing field was still null. It was populated at 1.05 seconds at z = 1.5256 m: approximately **1.53 m too far along the court**, with a lateral difference of 0.47 m.

The recorder polls post-step contact manifolds and requires a positive solver-contact count. That does not reliably capture the earliest impact in the tested case. See [physics contact recording](../../web/lib/game/physics.ts#L244) and [diagnostic results](2026-09-05/evidence/landing-probe.json).

**Impact:** landing markers and landing-derived feedback can be wrong even when the visible physical throw is plausible. The sampled trajectory is a separate measurement and is not invalidated by this finding.

**Before alpha:** capture the earliest ground impact reliably, including transient contacts during continuous collision detection. Preserve this ordinary release as a regression case and check contact location/time against the trajectory. Do not label a later sustained contact as first landing.

### 2. P1 — Dependency updates and a recoverable release are outstanding

The lockfile contains advisory-flagged packages. The most prominent direct dependency, `react-server-dom-webpack` 19.2.6, is affected by a Server Functions availability advisory, fixed in 19.2.8. The maintainer explicitly states that applications without a server are not affected by that vulnerability. The intended static export has no Server Functions endpoint, so the scan does **not** demonstrate that a visitor can exploit this issue in the planned deployment. See the [React maintainer advisory](https://github.com/react/react/security/advisories/GHSA-wx67-qw84-cm4g).

Other flagged branches include Vite development-server code, vinext/image-size and Cloudflare development tooling with miniflare, sharp, undici, ws and esbuild. These are principally build/development/server concerns for the configuration reviewed, rather than demonstrated vulnerabilities in the shipped browser game. Build environments still matter, and accidentally deploying a server would change the exposure.

The registry suggested these direct updates on the audit date:

| Dependency | Installed | Audit-suggested version |
| --- | --- | --- |
| react-server-dom-webpack | 19.2.6 | 19.2.8 |
| vinext | 1.0.0-beta.5 | 1.0.0-beta.9 |
| vite | 8.0.13 | 8.2.2 |
| @cloudflare/vite-plugin | 1.37.1 | 1.54.4 |

These are remediation candidates, not a compatibility-tested upgrade set. Update compatible React/framework/tooling versions together, regenerate the lockfile, then rerun the checks and dependency audit. Do not blindly force transitive versions. The detailed dependency report is linked below.

Also, this directory is **not currently a Git repository**, despite its location under `Github`. There is no local commit history to roll back to. Before release, preserve source and assets in version control or another durable versioned backup, pin the build runtime, verify a clean lockfile install and retain a known-good deployment artifact. The audit includes source and export fingerprints but is not a full backup.

### 3. P2 — The interface and physics disagree about readiness

**Confirmed in all 12 ordinary readiness probes.** [Penalty resolution](../../web/lib/game/physics.ts#L391) clears `settledFor` even when nothing is reset. [Throw completion](../../web/lib/game/scene.ts#L526) immediately sets the UI to ready for an unfinished row. A subsequent throw is rejected by physics until another 0.4 simulated seconds passes. In quarter-speed mode that is about 1.6 real seconds. The scene does not catch that rejection.

Penalty resets have a related contract problem: their 1.4-second presentation timer makes the range ready without checking whether physics has actually settled. See [the render loop](../../web/lib/game/scene.ts#L711).

**Before alpha:** give readiness one authoritative state, wait for both reset presentation and physical settling where needed, and make rejected input leave a clear, consistent UI. Test immediate repeat throws and slow-motion resets at the scene/physics boundary.

### 4. P2 — A court drag can change the settings of an already released throw

**Confirmed by source control flow; interactive browser reproduction pending.** A user can begin a court drag and press Space before releasing the pointer. `throwBone()` launches the body but does not clear the drag. Further pointer movement still changes `shot`, and pointer cancellation can restore its earlier value. The body has already received its launch velocity, but `finishThrow()` later builds the record from this mutable `shot`.

See [launch and recording](../../web/lib/game/scene.ts#L479) and [pointer handling](../../web/lib/game/scene.ts#L570).

**Before alpha:** snapshot launch settings at release, clear active gestures on launch/reset/mode changes, and prevent in-flight pointer changes. Verify mixed keyboard/pointer input and camera release while a drag exists. The journal should describe the settings actually applied to the rigid body.

### 5. P2 — Saved history can break the journal after corruption or a schema change

The [history loader](../../web/lib/game/scene.ts#L366) validates path coordinates and a few fields but accepts records without valid speed, loft, power, landing or duration data. The journal assumes these fields are present; for example, [release speed calls `toFixed`](../../web/components/game/throw-journal.tsx#L240). There is no component error boundary protecting the journal from such rendering errors. `Suspense` handles loading, not these failures.

**Impact:** a bad record left by an earlier version or local storage corruption could cause a persistent failure on reload. This is a local reliability issue; there is no public record-import endpoint in the reviewed app.

**Before alpha:** add full, bounded record validation and migration, a visible clear-history action, and an error boundary that keeps the court usable. Check missing fields, older versions and storage-write failures. The current “saved on this device” message should not promise success if storage rejects a write.

### 6. P2 — Camera errors are handled, but silent stalls have no recovery deadline

The permission helper has useful tests for rejection, retry, cancellation and a late permission grant. Video is requested without microphone access. Closing camera mode or hiding the tab stops tracks and terminates the worker.

However, [worker initialization](../../web/components/game/camera-throw.tsx#L308) has no timeout, and a [frame marked busy](../../web/components/game/camera-throw.tsx#L254) stays busy until the worker responds or reports an explicit error. A silent initialization/inference stall can leave camera mode stuck until the player closes or restarts it. There is no frame-response watchdog. Waiting for a user to answer a browser permission prompt is a separate, expected pending state and should remain cancellable.

**Before promoting camera mode:** add bounded startup/inference recovery, cancel arming on a stalled frame and offer retry or keyboard/touch fallback. Verify the complete permission flow in a real browser. Synthetic landmark tests cannot establish whether release timing, left/right aim or wrist spin feels correct with a moving person.

### 7. P2 — Historical comparisons lack physics and starting-position context

[Throw records](../../web/lib/game/types.ts#L12) contain release settings, surface, path and results, but no physics/model version or starting board state. The [comparison filter](../../web/components/game/throw-journal.tsx#L31) groups by surface and whether the old reset-count field exists. Throws made before and after bounce/collider changes can therefore be compared as if they used the same simulation. A shot into a full row is also compared with one into a nearly cleared row.

The UI already cautions that these are observations rather than an optimum, and that aim/power/remaining targets matter. That is helpful but does not identify changes in the underlying simulation.

**Before treating the journal as coaching:** version physics, collider/model and surface parameters; capture the initial board state or enough context to group comparable trials. Clearly separate incompatible historical data without deleting it. At minimum, begin a new comparison group after material physics changes.

## Physics, rules and real-world fidelity

The foundation is appropriate for this project: Rapier's Rust engine runs through its official JavaScript/Wasm package, while TypeScript owns the UI and Three.js renderer. A wholesale rewrite in Rust is not a prerequisite for release. The simulation uses fixed 120 Hz steps, continuous collision detection, eight solver iterations and 16 convex pieces per bone. Existing tests cover stable targets, assigned mass, gravity, guard knockdown, softer rebounds and surface-dependent sliding.

The generated collision asset approximates a repaired, non-watertight scan. Its reported decomposition concavity exceeded the requested threshold under the 16-piece cap. That is a fidelity limitation, not evidence that every collision is wrong. Test collisions and contact placement against the rendered shape at real scale before increasing complexity.

Target mass (0.25 kg), thrower mass (0.30 kg), uniform density, release height (0.75 m), friction, restitution and damping are assumptions. The source information sheet supplies dimensions/rules, not these physical measurements. Bone friction also currently comes from the selected ground preset, so changing ground changes bone-on-bone friction as well; separate material properties when calibrating. The ground is rigid geometry and does not simulate deformable soil or grass.

The aiming crosshair specifies direction toward the row. It does not guarantee an impact: loft/power determine arrival height and landing distance; shape, spin and contact determine deflection after landing. The dashed preview is a gravity-only approximation and does not include the simulation's small linear damping or subsequent collisions. There is no intentional random aim offset in the launch code. Random sound pitch does not affect physics.

Camera aim, release power and three-axis wrist spin are control estimates. They do not directly measure the velocity/spin of a real bone leaving the fingers. Fixed camera geometry assumptions, hand occlusion, motion blur and landmark uncertainty need recorded-sample validation. Keeping wrist spin marked experimental is appropriate.

The 10 m court, 3.66 m width, 20 soldiers, two guards and guard-first reset scheme broadly follow the information sheet. This remains unlimited practice: alternating ends, the hammer, end-of-round clearing and a full match are absent. Removing the oldest thrower before adding a thirteenth also changes the obstacle field. Those choices are acceptable for a clearly labeled practice range. A tilt threshold is the game's operational definition of “down”; it has not been validated against judging real bones.

**Calibration gate:** measure representative bone dimensions/masses, then compare ordinary releases and drops on known surfaces using independent video/measurements. Compare trajectory, first contact, rebound, runout, direction after impact and spin. Set tolerances before using those trials as validation; do not tune and validate solely on the same samples.

## Performance and mobile readiness

There are sensible provisions: device-pixel-ratio/shadow limits on touch devices, lazy camera/journal loading, a worker for vision inference, one camera frame in flight at a time, and suspension when the document is hidden.

There is still substantial work per frame: up to 34 dynamic bodies with 16 colliders each, a detailed terrain collider, physics at 120 Hz, main and target-monitor rendering, shadows, and optional CPU pose plus two-hand inference at up to roughly 22 submissions per second. The visible scene continues stepping/rendering when idle. Trail geometry is repeatedly recreated. These are profiling candidates, not measured mobile failures.

The whole export is 35.55 MiB, but it is not all downloaded at startup: SIMD and non-SIMD vision Wasm files are alternatives, and vision loads for camera mode. One vision Wasm runtime plus pose/hand models totals about **22 MiB uncompressed, or 13 MiB with local gzip**. Actual CDN compression, transferred bytes and startup time have not been measured. The main scene chunk is 2.27 MB uncompressed, separate from the 0.51 MB Three.js chunk.

Before a mobile claim, test a recent iPhone/Safari and a representative midrange Android/Chrome, plus desktop Chrome. Check portrait/landscape, touch capture, browser toolbars, denied camera permission, returning from background, both hands, poor lighting and repeated resets. Run at least a ten-minute session with camera on, then off. Record cold start, frame-time distribution, inference cadence, memory growth and visible thermal slowdown. A reasonable initial acceptance target is sustained 30 fps on the selected midrange phone, with responsive touch and no stuck throw states; this is a proposed target, not a measured result.

If profiling requires it, reduce or adapt shadows, target-monitor rendering and vision cadence, and avoid rebuilding unchanged trail geometry. Profile before reducing collision accuracy.

## Hosting, DDoS, privacy and abuse

### Keep the first release static

[The export configuration](../../web/next.config.ts#L2) and local hosting manifest (`web/.openai/hosting.json`, not committed) select `dist/client`, with no D1/R2 bindings. Publish only that static artifact through the selected host. The build also produces server tooling/output; that is not needed to serve this game. Do not expose the laptop's development server as the production site.

Cloudflare documents free, unlimited requests to Workers static assets, while Worker-script execution is priced separately; routing requests through a Worker first changes that behavior. Its DDoS managed rules are enabled by default on onboarded zones on Free/Pro/Business plans. These support the low-overhead static approach, but they do not verify this account's setup or guarantee uninterrupted service. See [static-asset billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/) and [DDoS setup](https://developers.cloudflare.com/ddos-protection/get-started/).

For the alpha, verify HTTPS, the selected static routing, account access protection, deployment rollback and any enabled paid features. No custom DDoS service, player login or CAPTCHA is justified by the current game architecture. If a shared API, upload flow or leaderboard is added, reassess input limits, rate limits, storage quotas, moderation and server-side score validation then. Client-side scores should never be trusted for prizes or shared rankings.

### Add and verify production headers

There is no `_headers` file or application-owned policy for CSP, framing, camera permissions, MIME sniffing or referrers. This is a missing hardening layer, not a demonstrated script-injection vulnerability. The host may supply defaults; deployed responses were not examined.

Define a tested policy that limits resources/workers to the required origins, limits camera access to the application, disables microphone access and controls framing. Apply an appropriate referrer policy and `nosniff`. Cloudflare supports static response policies through [its `_headers` mechanism](https://developers.cloudflare.com/workers/static-assets/headers/).

Do not paste in an untested strict CSP: the exported home page contains inline framework scripts and both Rapier and MediaPipe compile Wasm. The policy must account for those actual requirements without broadly allowing arbitrary script execution. Verify the camera, worker and models under the final policy.

Use long-lived caching for content-hashed assets. HTML, the currently un-hashed worker URL and stable model/runtime paths need revalidation or explicit release versioning so old and new components are not mixed. Check Wasm/model content types and successful loading from the final HTTPS origin.

### Privacy and moderation exposure is small

The reviewed owned code processes frames and landmarks locally; it has no upload path. The optional nickname is rendered as React text and limited to 24 characters; the latest 30 throws are stored locally. There is no public username directory, chat or shared content to moderate. The optional WebMCP methods expose the local range through a supporting browser, not an internet server endpoint; their throw inputs are bounded and validated.

Keep the existing empty-hand instruction and honest camera explanation. Verify the deployed network requests before making a final privacy statement, including anything the host adds. Basic HTTP hosting logs may still contain request metadata even when video stays on-device. A clear-history action would make local data control more complete.

### Distribution notices need completion

The export has a [MediaPipe notice](../../web/public/vision/NOTICE.txt#L1) identifying sources and the Apache-2.0 SDK license, but it does not contain the full license text. Audit the shipped SDK/model/library notices and include the required license/copyright material in the distribution; Apache's redistribution terms include supplying a license copy. See the [Apache-2.0 license](https://www.apache.org/licenses/LICENSE-2.0).

The source bone is user supplied, and the footer already states inspiration and no affiliation with Bunnock.com. This audit did not establish model ownership, domain availability, trademark clearance or the legal adequacy of the wording. A domain purchase and public deployment remain separate decisions.

## Concrete release gates

### Before a limited alpha

1. Fix first-contact recording and the readiness contract, including slow motion. Add regression coverage for both demonstrated failures.
2. Freeze released-shot settings and clear overlapping input gestures.
3. Validate/migrate saved records, isolate journal failures and provide clear-history recovery.
4. Update compatible dependencies, make lint useful by excluding vendor/generated files and reviewing owned diagnostics, and pass a clean production build and tests on a pinned runtime.
5. Preserve a recoverable source/build version, complete distribution notices and configure the static deployment and security/cache headers.
6. Perform production-browser smoke tests: a full sequence of throws/resets, guard penalties, history reload, keyboard/touch, camera allow/deny/retry/close/background, and confirm no unexpected frame uploads. Add camera stall recovery before including it as a working alpha feature; otherwise label it unavailable on unsupported devices and retain manual play.

A small test group can then use the alpha without accounts. An unlisted public link is still publicly accessible; it is not access control. Collect concrete observations about missed releases, aiming confusion, first-contact accuracy, frame rate and completed sessions.

### Before a broad launch

Pass the real-phone and longer-session tests, confirm accessibility of the control alternatives and dialogs, version analytics comparisons, and verify production monitoring/rollback. Treat any telemetry as a deliberate privacy choice rather than silently adding camera or landmark collection. Fix measured failures; do not require multiplayer, authentication or a server just to launch the practice range.

### Before real-world coaching claims

Complete independent physical calibration and camera validation. Keep the journal framed as feedback about this simulation until that evidence exists.
